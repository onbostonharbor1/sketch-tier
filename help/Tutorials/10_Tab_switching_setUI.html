Tutorial 10: Tab switching (setUI)

Written 6 November 2026 for Sketchpad on branch claude/tier-a. Files and functions are named rather than given line numbers, so the text stays right as lines move: in VS Code press Ctrl+P to open a file and Ctrl+Shift+O to jump to a function, or look it up in docs/FUNCTIONS.md. "Watch it" lines use the browser's developer tools (F12): Sources to set a breakpoint, Console to run a line.

Every click on a main tab goes through one file, ui/setUI.js. It decides whether a tab starts fresh or is restored, keeps fast clicks from tangling, reports failures by stage, and carries requests from one tab to another. Read this tutorial with the debugger open: tab switching is easier to watch than to read.

10.1 The six TabSpecs

Read

ui/setUI.js (TabRegistry), then each tab's spec: HomeTabSpec (ui/home/home.js), DrawTabSpec (ui/draw/draw.js), PatternsTabSpec, GalleryTabSpec, UtilityTabSpec, FiguresTabSpec.

What happens

A TabSpec is an object describing a tab: its name and theme, the regions it uses, init(restored) to start it, restore() to show it again from its remembered state, save() to give that state, and builders for its subtabs, caption, text, action and sketchpad. setUI knows nothing about what a tab shows; it only calls these.

10.2 The decision order

Read

activateTab, initTab, restoreTab in ui/setUI.js.

What happens

For the tab clicked: if its needsUpdate is set (after a rebuild), clear it and start the tab with init(true); otherwise, if it has remembered state (uiState.<tab>.saved), restore it; otherwise start it fresh with init(false). Both init and restore are preceded by clearDivs. The first start (START_APP) is Home. Then uiState.activeTab is set and the tab button marked.

Note what is not here: nothing calls a tab's save() when you leave it. State is written through immediately as you work, so by the time you leave, uiState.<tab>.saved already says where you were.

10.3 Fast clicks: the chain and the ticket

Read

setUI and activationChain, latestTicket in ui/setUI.js.

What happens

Switches run one at a time: each call waits for the one before (the chain). Every call takes a ticket number; when its turn comes, if a newer click has arrived meanwhile, it does nothing. So clicking four tabs quickly ends on the last one, with its own content and colours, never a mixture.

10.4 Stages and reporting

Read

activateWithReport and runSetUI in ui/setUI.js.

What happens

runSetUI does the work in named stages: disable overlays, apply theme, activate the tab, then the launch intent. If anything throws, activateWithReport reports it with the stage it reached ("Switching to the draw tab (stage ...)") to the red bar, and timing is recorded for instrumentation.

Watch it

Utilities > Commands > Record timings, switch tabs, Show timings.

Try

10.5 The launch intent

Read

runSetUI (the launch intent stage), uiState.launch, and the readers: consumeLaunchIfForDraw (ui/draw/draw.js), the Figures launch from Home.

What happens

One tab can ask another to open something: Home opens a Draw object or a saved figure. It fills uiState.launch (pending, source and target tab, what to open) and calls setUI for the target. The target reads the request during its start and clears it; runSetUI clears whatever is left after. The request survives until read, which is why it works even when the target is restored rather than started.

10.6 needsUpdate and the complete rebuild

Read

ui/rebuildSync.js (syncSystemStateAfterRebuild), and the per-tab refresh functions after an edit (refreshGalleryFromManifestEdit and friends).

What happens

After an edit that changes lists (Edit Manifest, Archive, Save figure), the list caches are forgotten and every tab is marked needsUpdate, so the next time you show it, it starts with init(true) and reads everything again. Nothing is patched in memory.

10.7 Start-up

Read

onDomContentLoaded in ui/setUI.js, and tutorial 1.3.

What happens

Menus, overlays, canvas layers, the tab buttons' click handlers, then setUI(START_APP). If that fails, a message is put in #text naming the stage, so you never get a blank page.

10.9 The Vite trap

Read

Help > Design > Subsystems > Tests and checks (One trap).

What happens

When a source file is edited while Vite is running, Vite serves the changed file under a new address. A test that imports the plain address then gets a second, fresh copy of the module, including a second uiState that thinks Home is active. It looks like a tab-switching bug but is not one. Restart Vite before running browser tests after editing code.

None.
